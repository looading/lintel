# Lintel 的 AI 接入与协作约定

AI native 覆盖两层：AI 能理解和修改框架，业务应用也能向 AI 提供明确、可验证的操作。业务仍围绕状态、消息、任务和服务组织，不维护第二套窗口或执行循环。

## 开发协作

`AGENTS.md` 约定源码边界、线程与权限规则、定向验证和发布约束；`llms.txt` 提供短入口；`lintel.project.json` 提供版本化目录。CLI 的 `describe --json` 与该目录同源，输出可由程序解析，发现阶段不执行构建、下载或用户代码。

生成应用同时得到面向消费项目的 AGENTS 与 llms 索引。框架说明留在 `.lintel/framework`，业务从自己的 `src/`、Cargo feature 和 CLI 开始。历史构建产物、依赖缓存和私钥不属于模型应扫描的项目上下文。

每项能力分别记录实现状态和验收边界。目标检查不能写成实机运行，零匹配或过滤测试不能写成通过；已经通过的检查在相关内容未变化时直接复用。普通任务不启用 AI Dev Loop。

## 应用中的 AI 工具

首批可选 `agent` 能力提供模型供应商无关的工具目录与执行契约。工具用名称、描述、输入 schema 和 effect 声明意图，执行端用 Rust 类型反序列化与业务校验；schema 元数据不被冒充成完整 JSON Schema 校验器。

工具会话由应用显式授权，并绑定现有 AppContext 与 TaskScope。调用使用已有受管任务，提供有界输入、输出、并发、进度和取消；关闭会话只影响该会话，窗口或应用关闭继续使用原生命周期清理。原生 UI 变化通过既有 Message/Task 或桌面服务完成。

发现工具不等于授予执行权限。模型返回的名称、参数和 effect 不能修改授权；同进程 Rust handler 仍是受信任代码，不声称被策略隔离。进度和错误不默认记录用户请求正文、提示词或凭据。

上下文启动入口让原生业务在插件与服务启动后取得句柄，并在失败时返回错误、执行原有清理。既有 application/multi_window 用法保持兼容，避免业务使用全局变量或 OnceLock 来传递服务。

可选 `multiprocess` 将独立服务接入同一应用生命周期。工具 handler 可以显式调用 typed 进程服务；工具授权与进程目录授权独立检查。进程隔离不自动扩大 AI 权限，也不改变远端副作用的取消语义。详见[多进程服务](multiprocess.md)。

## 分批落地

| 本批交付 | 验收 |
|---|---|
| Agent 入口文档与同源目录 | 本地链接/JSON 检查，发现输出的 schema/version/无副作用检查 |
| CLI describe 与消费项目指南 | CLI 解析测试、真实 new 生成项目、可移植内容检查 |
| 上下文原生启动 | 原 API 源兼容、服务可用、初始化失败清理与错误返回 |
| 可选工具执行基础 | 类型错误、拒绝授权、输入/输出/并发/进度上限、取消、会话/窗口/应用关闭回归 |
| 外部单依赖示例 | 通过公共 facade 使用服务与工具，实际启动/退出或明确记录平台限制 |

模型 provider、token streaming、会话历史/RAG、远程 MCP/HTTP transport 和运行中动态插件作为独立适配层推进。它们不能因工具路由存在就被标记为已经实现；不会在默认启动时自动连接模型或扩大文件、网络、系统权限。
